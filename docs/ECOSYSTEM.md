# PodApp 生态路线

目标不是让仓库看起来热闹，而是缩短三段时间：

1. 新用户从看到项目到首次成功运行。
2. 创作者从产生想法到发布 Pod 或皮肤。
3. 维护者从收到反馈到复现、合并和发布。

## 产品入口

- 用户入口：一分钟安装、五分钟跑通一个内置 Pod、清晰的权限确认。
- 创作者入口：界面内复制 AI 开发指令，产物可验证、可打包、可拖入安装。
- 贡献者入口：Pod、皮肤、翻译不要求 Rust；核心变更先 Issue 后 PR。
- 分发入口：GitHub Release、包管理器和可信 Pod/皮肤索引使用同一份版本元数据。

## 展示机制

规划 `showcase/` 索引，每项只保存元数据、预览图、仓库地址、许可和最低版本，不复制第三方
源码。合并展示项前自动验证 ID、版本、下载地址和权限摘要。README 每月轮换少量优秀作品，
完整目录放独立页面，避免首页无限增长。

建议标签：

- `good first issue`：范围清晰、无需理解核心协议；
- `pod`、`skin`、`translation`：按贡献路径分流；
- `needs reproduction`：缺最小复现；
- `breaking change`：影响协议或持久化格式；
- `showcase`：申请进入生态展示。

## 发布节奏

- 每个 PR 通过 Windows CI、核心测试和前端构建。
- Release Notes 按“用户变化 / 创作者变化 / 修复 / 兼容性”组织，并署名社区贡献者。
- 大版本前发布候选版；协议字段先文档、再解析、最后设为必填。
- 自动更新器上线前必须有签名、回滚、校验和与旧版升级真机验证。

## 增长验证

默认不采集侵入式遥测。公开可验证指标优先使用 GitHub Release 下载、Stars、Forks、
首次贡献者、Pod/皮肤提交数、Issue 首次响应时间和文档入口转化。任何产品遥测都必须显式
说明字段、用途、保留期和关闭方式。

每次对外发布只讲一个可复现故事：

> 安装泊舟，拖入一张图，运行一个确定动作；再让 AI 用同一个 Action ID 无头执行。

推广渠道应链接到同一个 Release 和同一个 90 秒演示。中文社区可提交阮一峰科技爱好者周刊
自荐；全球开发者渠道优先 GitHub Release、Show HN、Reddit 对应社区和产品演示平台。
先保证安装与复现，再扩大曝光。

## 参赛准备

仓库长期维护 [`SHOWCASE-KIT.md`](./SHOWCASE-KIT.md)，每次比赛只补“本次期间新增内容”：

- 真实问题与目标用户；
- 可测试安装步骤；
- 90 秒主流程；
- 人与 AI 共用动作核心的架构证据；
- 权限和安全边界；
- 已有代码与比赛期间新增代码的明确披露；
- 公开仓库、发布包和短演示视频。

不要为比赛临时复制一套演示逻辑。评委操作的应当就是用户下载到的版本。
